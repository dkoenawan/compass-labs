## 1. System Context

### What It Does

compass-labs' vision, mission, scope and non-goals are stated once, in the README's [Project anchor](../../README.md#project-anchor). This document doesn't restate them; it describes how the plugin is built to meet them.

compass-labs is a Claude Code plugin. It ships:

- **Skills** (`skills/*/SKILL.md`), invoked as `/compass-labs:<skill-name>` or preloaded by agents. Each is a Markdown workflow the model follows.
- **Agents** (`agents/*.md`): the session orchestrator and one phase agent per Feature phase.
- **Hooks** (`hooks/`): shell scripts that enforce the session lifecycle's file set, ownership, freezing and commit points.
- **Scripts and templates** inside the skills, run with bash, jq, git and the `gh` CLI.

Everything runs on the developer's machine, against their local filesystem and git history. There is no server, container or cloud component.

### Who It's For

See the [Project anchor](../../README.md#project-anchor)'s vision and scope. In practice, the people who run it are developers using Claude Code, in any repo the plugin is installed into.

### External Systems

| GitHub (via `gh` CLI) | One issue per session, with `phase:*` labels and a milestone comment per phase transition (driven by the `session` orchestrator); issue comments and pull requests from `task-executor` |

## 3. Key Architectural Decisions

- **Skill-as-Markdown**: All skill logic lives in `SKILL.md` files with YAML frontmatter — human-readable, diff-friendly, and model-agnostic. No compilation step; any Claude model can execute them.

- **Opt-out scaffolding over opt-in**: The `init` skill presents the full stack by default and asks what to *remove*, reducing cognitive load and keeping the default path near-zero friction.

- **Template-clone over direct generation**: `init` clones a pre-built GitHub template rather than generating files from scratch — faster, lower-token, and keeps generated projects in sync with upstream template improvements.

- **Tiered codebase investigation**: The `explore` skill reads documentation before code (Tier 1), then structure files (Tier 2), then up to 5 targeted source files (Tier 3), stopping as soon as the focus is answered. This bounds token cost by task scope.

- **Dedicated docs branch**: `doc-maintainer` always operates on `chore/claude-maintain`, never on `main` or feature branches, keeping auto-generated commits separate from source history.

- **Approval gates before file generation**: Both `plan` and `brand-designer` require explicit user sign-off on synthesised briefs/specs before writing any files, preventing misinterpreted output from reaching disk.

- **Hook-enforced session lifecycle**: A main-session orchestrator runs each session through one phase agent per phase, and each phase agent owns one artifact in `docs/sessions/{date}-{slug}/`. Plugin hooks, not prompt instructions, enforce the folder's file set, artifact ownership, freezing after each milestone, and one commit per logged decision. See [ADR-002](../registry/decisions/002-session-lifecycle.md) and [patterns](../registry/patterns.md).

- **Framing before requirements, anchored to the project**: Every session type runs one shared framing skill, which names no phase, before writing its problem statement and requirements. Each type plugs in through a `framing` block in its workflow file and per-type standards files. New work is checked against the README's marked project anchor, which only the orchestrator writes. A Feature session's Define output is a `define/` folder: one artifact with a fixed file set, owned and frozen as a unit. See [ADR-003](../registry/decisions/003-framing-and-project-anchor.md).

- **Per-domain staleness tracking via frontmatter**: Each `docs/<domain>/overview.md` carries a `last_updated` YAML date; the `find-stale-domains.sh` script reads this to detect which domains need refresh, enabling targeted incremental updates.
