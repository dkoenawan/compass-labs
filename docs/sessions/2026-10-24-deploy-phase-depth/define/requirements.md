# Requirements: Deploy phase depth

> Part of [index](index.md) · Define

## Requirements

EARS syntax. Each requirement has one acceptance criterion in Given/When/Then form. IDs are never reused; a dropped requirement is struck through, not deleted. A Won't meaning "never" is struck through with its reason; a Won't meaning "later" moves to the Deferred table below.

- **"L1, deployment setup"** means creating or updating how a repo's deployable parts get deployed. It's needed when a repo starts and whenever its architecture changes. **"L2, session release"** means getting one session's change to its target (staging, production, or for compass-labs a tagged plugin release). See [problem.md](problem.md).
- **"Deploy declaration"** means the repo's own statement of what deploy means for it, kept in the repo, in a form Design chooses. What it must state is set by REQ-001.
- **"Routine step"** means a declared step the repo marks as safe to run without asking the user. **"Production-affecting step"** means a declared step the repo marks as needing the user's own instruction. A merge is always treated as production-affecting.
- **"Release record"** means the session's `release.md`. **"Deploy standard"** means the standard skill this session adds for Deploy and its release record.
- **"Merge-triggered pipeline"** means compass-labs' own L1 setup: automation that runs on the repository host when a pull request is merged into the default branch. The mechanism is Design's choice.

| ID | Requirement | Priority | Serves | Acceptance criterion |
|---|---|---|---|---|
| REQ-001 | The Deploy standard shall define what a deploy declaration states: the L1 setup for each deployable part, the L2 release steps, which steps are routine and which are production-affecting, the confirmation check, the rollback, and whether a release runs inside the feature session or as its own session. | Must | NEED-02, OUT-03 | Given the Deploy standard alone, when a reviewer writes the declaration for the fixture repo `fixture-service` (one web service, a staging target and a production target), then each of the seven items has a named place, and the result needs nothing beyond the standard. |
| REQ-002 | Where a repo has a deploy declaration, the Deploy phase shall take the release steps, the confirmation check and the rollback from it, and the release record shall name the declaration as their source. | Must | OUT-01, OUT-03 | Given compass-labs declares its L2 steps as "bump the version, commit, push the session branch, mark the PR ready", when this session's Deploy runs, then `release.md` lists those four steps, names the declaration as their source, and doesn't re-derive them from `Taskfile.yml` or past release records. |
| REQ-003 | If a repo has no deploy declaration, then the Deploy phase shall stop before running any deploy step and tell the user how to declare one. | Must | OUT-02 | Given the fixture repo `fixture-no-declaration` has no deploy declaration, when its session's Deploy phase starts, then no command from the repo is run, no file outside the session folder changes, and the agent returns `blocked` with a message naming the deploy declaration and the place in the Deploy standard that describes it. |
| REQ-004 | If a repo's deploy declaration leaves out an item REQ-001 requires, then the Deploy phase shall stop before running any deploy step and name the missing item. | Should | OUT-02 | Given `fixture-service`'s declaration states no rollback, when Deploy starts, then no deploy step runs and the agent returns `blocked` naming "rollback" as missing. |
| REQ-005 | When the Deploy phase runs a release, it shall run every step the declaration marks as routine without asking the user, choosing any version bump by the repo's declared versioning rule and recording the reason. | Must | OUT-01 | Given compass-labs at v2.2.1, PR #77 in draft, and this session adding a skill, when this session's Deploy runs, then `.claude-plugin/plugin.json` reads `2.3.0` in a commit on `feat/30-deploy-phase-depth`, the branch is pushed, PR #77 is marked ready, `release.md` gives "MINOR: a new skill" as the bump reason, and the user is asked no question before the Deploy gate. |
| REQ-006 | If a declared step is production-affecting, then the Deploy phase shall not run it until the user's own message instructs it, and shall record it in the release record as waiting for that instruction. | Must | OUT-03, NEED-01 | Given `fixture-service` declares "deploy to staging" as routine and "deploy to production" as production-affecting, when Deploy runs, then the staging step runs, the production step doesn't, and `release.md` lists "deploy to production: waiting for the user's instruction". |
| REQ-007 | When the Deploy phase has run the release steps, it shall run the declaration's confirmation check and record the check and its result in the release record. | Must | OUT-03 | Given `fixture-service` declares the confirmation check `./check-health.sh`, which prints `healthy` and exits 0, when Deploy has run the staging step, then `release.md`'s confirmation section names `./check-health.sh`, quotes `healthy`, and records it as passed. |
| REQ-008 | If the declared confirmation check fails, then the Deploy phase shall record the failure and the declared rollback in the release record, and shall not report the release as complete. | Must | OUT-03, NEED-03 | Given `./check-health.sh` prints `unhealthy` and exits 1 after the staging step, when Deploy records the result, then `release.md` records the check as failed with `unhealthy`, shows the declared rollback, and the agent returns `blocked`, not `done`. |
| REQ-009 | When a repo has no deployment setup declared, or the session's frozen design adds or changes a deployable part the declaration doesn't cover, the Deploy phase shall treat L1 as needed, run the declared setup for that part before the session release, and record in the release record that L1 ran and why. | Must | OUT-05, OUT-06 | Given the fixture repo `fixture-new-part`, whose session's frozen design adds a container `billing-service` that its declaration doesn't cover, when Deploy runs, then `release.md` records "L1: needed, `billing-service` has no deployment setup", and the L1 entry comes before the L2 entry. |
| REQ-010 | While a session changes no deployable part and the repo's deployment setup is declared, the Deploy phase shall run only the session release, and record in the release record that L1 wasn't needed. | Must | OUT-05 | Given `fixture-service`'s session changes only the text of an existing page, when Deploy runs, then `release.md` records "L1: not needed, no deployable part changed" and only L2 steps run. |
| REQ-011 | If L1 is needed for a part and the declaration gives no way to set that part up, then the Deploy phase shall stop before the session release and name the part. | Should | OUT-05 | Given `fixture-new-part`'s declaration has no setup for `billing-service`, when Deploy finds L1 is needed, then no L2 step runs, and the agent returns `blocked` naming `billing-service` as having no declared setup. |
| REQ-012 | Where the deploy declaration says a release runs as its own session, the Deploy phase of a feature session shall run no release step, and shall record in the release record that the change waits for a release session. | Should | NEED-02 | Given `fixture-service` declares "release: own session", when a feature session's Deploy runs, then no release step runs, and `release.md` records "release: waits for a release session" and still has its completeness section. |
| REQ-013 | Where the deploy declaration says the repo has nothing to deploy, the Deploy phase shall run no deploy step and record that the session has nothing to deploy. | Could | NEED-02 | Given the fixture repo `fixture-docs-only` declares "no deployment", when Deploy runs, then no command from the repo is run, and `release.md` records "nothing to deploy, per the declaration". |
| REQ-014 | The Deploy standard shall state, for each depth tier, which sections the release record must have, from: the lifecycles run and why, the release strategy, completeness, the steps run, the confirmation, the rollback, and the change record. | Must | OUT-04 | Given the Deploy standard, when a reviewer reads it for full, short and skip tier, then a table gives, for each of the seven sections, whether it's required at that tier and what it must contain. |
| REQ-015 | If the release record is missing a section the Deploy standard requires at the session's framing tier, then the Deploy milestone gate shall refuse the milestone and name the missing section. | Must | OUT-04 | Given a full-tier session whose `release.md` has no rollback section, when the user is asked to approve the Deploy milestone, then the gate refuses it and names "rollback" as missing, and `log.md`'s `milestone` stays at `test`. |
| REQ-016 | The Deploy standard shall name, for each release-record section, the established framework it draws on, with an adopt, adapt or reject verdict and its reason. | Should | NEED-03 | Given the Deploy standard, when a reviewer checks the rollback and change-record sections, then each names at least one established framework (for example ITIL 4 change enablement for the change record), with a verdict and a one-line reason. |
| REQ-017 | The Deploy phase shall run the release-completeness check before any deploy step, in both L1 and L2. | Must | NEED-03 | Given compass-labs' `marketplace.json` lists a skill whose `SKILL.md` has a TODO body, when Deploy starts with L1 needed, then no L1 or L2 step runs, and the agent returns `blocked` naming that skill. |
| REQ-018 | The compass-labs repo shall have a deploy declaration that states its L2 release as routine steps (bump the version by its versioning rule, commit, push the session branch, mark the PR ready), its L1 setup as the merge-triggered pipeline, and the steps after the merge that the pipeline doesn't run. | Must | OUT-01, OUT-06 | Given the compass-labs repo at the end of Implement, when a reviewer checks it against REQ-001's seven items, then each has an entry, the four L2 steps are marked routine, and the merge is marked production-affecting. |
| REQ-019 | The merge-triggered pipeline shall be checkable before any merge, by a run that reports the tag it would create for a branch's plugin version, without creating a tag or a release. | Must | OUT-06 | Given `feat/30-deploy-phase-depth` with `plugin.json` at `2.3.0`, when the check runs before the merge, then it reports `compass-labs--v2.3.0` for the branch head, and `git ls-remote --tags origin` shows no new tag. |
| REQ-020 | When a pull request that changes the plugin version is merged into compass-labs' default branch, the merge-triggered pipeline shall create the release tag on the merge commit and publish the release, with no step run by the user. | Must | OUT-06 | Given PR #77 with `plugin.json` at `2.3.0`, when the user merges it, then `git ls-remote --tags origin compass-labs--v2.3.0` resolves to the merge commit, the repository host lists a published release `compass-labs--v2.3.0`, and the user ran no command after the merge. |
| REQ-021 | When a pull request that doesn't change the plugin version is merged into compass-labs' default branch, the merge-triggered pipeline shall create no tag and publish no release. | Should | OUT-06 | Given a docs-only PR merged with `plugin.json` left at `2.3.0`, when the pipeline runs, then no tag or release is added, and the pipeline's run record says no version change was found. |
| REQ-022 | If the release tag for the merged version already exists, then the merge-triggered pipeline shall fail visibly and leave the existing tag and release unchanged. | Should | OUT-06 | Given `compass-labs--v2.3.0` already exists at commit `abc1234`, when a second PR with `plugin.json` at `2.3.0` is merged, then the pipeline's run is marked failed, naming the existing tag, and the tag still resolves to `abc1234`. |
| REQ-023 | The release record shall list every step after the merge that the merge-triggered pipeline doesn't run as the user's step, with the command to run. | Should | OUT-06, NEED-01 | Given this session's Deploy, when `release.md` is written, then any step left to the user after the merge (for example refreshing the local plugin install, if Design leaves it to the user) is listed with its command, and no step the pipeline runs is listed as the user's. |
| REQ-024 | When a version-changing pull request is merged into compass-labs' default branch, the merge-triggered pipeline shall make the release tag visible on the remote. Measure: see [quality.md](quality.md#nfr-measures). | Could | OUT-06 | Given PR #77 is merged at a recorded time, when `git ls-remote --tags origin compass-labs--v2.3.0` is polled every minute, then the tag appears within 10 minutes of the merge. |
