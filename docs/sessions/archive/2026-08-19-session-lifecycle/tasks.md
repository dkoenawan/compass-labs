## Deviations from design

- **Task 2**: workflow definition is `skills/session/workflows/feature.json`, not `feature.yaml` as task 2's own text and design.md's D3 mention it. Per the implement-agent brief: hooks are bash and `jq` is available in this repo, `yq` is not, so JSON keeps later hook tasks (4+) dependency-free. Schema is flat (`phases[]` with `phase`, `order`, `owner_agent`, `artifact`, `milestone`, `gh_label`, `conversational`, plus a `session_level` block for the D1 file allowlist and log ownership) so `jq '.phases[] | select(.phase=="…")'` is enough for later hooks. No separate README — the schema is documented via a `"$comment"` field inside the JSON. *(Orchestrator review, batch 1: not a real deviation — D3 says "yaml-style" and the build table says `feature.*`.)*
- **Task 5**: extended `feature.json` (from task 2) with a `github` block (`type_label`, `type_color`) and a `gh_color` per phase, using the colors from design.md's D5 one-time-setup snippet. Not in task 2's or task 5's original scope, but `gh-setup.sh` needs label colors from somewhere and the workflow file already carries every other `gh_label`, so colors moved in beside them rather than being hard-coded in the script.
- **Task 8, P8 verification result**: `claude --plugin-dir /home/su-sentinel/private/compass-labs --agent compass-labs:orchestrator -p "…"` **resolves correctly** — the plugin-namespaced agent starts as the main session and replies as the orchestrator. That much of P8 is confirmed. **But** the `skills: [compass-labs:session]` (also tried bare `session`) frontmatter field did **not** inject the session skill's content into context in this run (CLI 2.1.281): the agent knew the skill's *name* (from its own system prompt) but, unprompted, said the skill's content "isn't actually in my context" and it would need to read the file from disk first. This contradicts the documented behavior ("skills: field... Full skill content is injected into the subagent's context at startup" — code.claude.com/docs/en/sub-agents), at least for the top-level `--agent` case (as opposed to a subagent spawned via the `Agent` tool, which this wasn't tested against). Mitigation applied in `agents/orchestrator.md` itself: an explicit fallback instruction telling the orchestrator to read `${CLAUDE_PLUGIN_ROOT}/skills/session/SKILL.md` if the skill's content isn't already visible. Re-tested after adding it — the orchestrator then correctly read the file and reported its actual mode-dispatch contents. Recommend the same defensive line in every phase agent (task 9) and doc-maintainer/close (task 10) rather than relying on `skills:` preload alone until this is root-caused against a specific CLI version.
- **Task 8, tools**: design.md's D3 illustrative list was `Agent, Bash(gh *), Read, Edit, Write` ("tools that include" — not stated as exhaustive). The orchestrator's actual job (per `skills/session/SKILL.md`, written after that D3 note) also needs plain `git commit`/`git push` and to run the plugin's own scripts (`gh-setup.sh`, `gh-milestone.sh`, `check-traceability.sh`), none of which fit a `Bash(gh *)`-scoped tool. Used unscoped `Bash`, plus `SendMessage` (relaying answers to a paused phase agent — D3 main loop step 2), `AskUserQuestion` (milestone gate / question relay), `Glob`/`Grep` (scanning `docs/sessions/*/log.md` for the session list). Not treated as a deviation needing a decision — design's list was explicitly non-exhaustive — but flagged here since it's a real expansion of what D3 sketched.
- **Task 9**: the shared D4 contract text lives at `skills/session/reference/phase-agent-contract.md` and every phase agent tells Claude to **read it explicitly** (`Read ${CLAUDE_PLUGIN_ROOT}/skills/session/reference/phase-agent-contract.md`) rather than preloading it via `skills:`, given task 8's finding that `skills:` preload didn't reliably inject content via `--agent`. `define`, `design` and `test` reference the `requirements`/`design`/`verification` skills only in a body TODO comment, not in frontmatter — those skills don't exist until #26/#27/#29, and loading a nonexistent skill via `skills:` hasn't been verified safe. `close` does preload `compass-labs:doc-maintainer` in frontmatter, since that skill already exists in this repo and D6 names it directly. Spot-verified `compass-labs:implement` resolves via `--agent` the same way the orchestrator did in task 8.
- **Task 11**: task 9's original `agents/close.md` said the Close agent itself runs `git mv docs/sessions/{slug}/ docs/sessions/archive/{slug}/`. That's corrected here: the **orchestrator** runs the move (via the new `archive-session.sh`), never the Close agent, because `status: archived` has to be committed to `log.md` (orchestrator-only) *before* the move — the guard hook blocks all writes under `archive/` afterward, orchestrator included, so the ordering only works one way. `agents/close.md` and `skills/session/SKILL.md`'s new "Close milestone" section were both updated to match; `skills/session/reference/close-foldback.md` spells out "what you don't do" explicitly so this doesn't regress.
- **Task 12**: removed `hooks/validate-spec.sh` entirely, not just its session-folder check — the script's only job *was* that check (validating `docs/sessions/*/overview.md` against a hard-coded DB/Backend/Frontend section list). Nothing else was in the file, so once that check was retired there was nothing left to retire it *from*. Its PostToolUse `hooks.json` entry was removed with it. Checked `skills/plan/SKILL.md` for a `validate-spec` reference — there is none, so no note was needed there; `plan` itself was left untouched.
- **Task 14, `stop_hook_active` finding**: checked (via the Claude Code hooks docs) what fields the `Stop` hook's input carries. It does **not** document a `stop_hook_active`-style field the way some other agent frameworks' stop hooks do — the fields present are `session_id`, `prompt_id`, `transcript_path`, `cwd`, `scratchpad_dir`, `permission_mode`, `effort`, `hook_event_name`, `agent_id`/`agent_type`, `last_assistant_message`. `hooks/session-commit-guard.sh` still reads `.stop_hook_active` defensively (`// empty`) and would skip straight to "allow" if it were ever `"true"`, but the actual loop guard is the documented fallback: a per-`session_id` consecutive-block counter in a state file under `${TMPDIR:-/tmp}/compass-session-commit-guard/`, reset the moment a check passes. Not treated as a blocking deviation — the task's own wording anticipated this ("check whether... and use it if present").
- **Task 14, shared helper**: factored the "does `log.md` have an uncommitted D2 heading of type X" check into `hooks/lib/session-log.sh` (`session_log_has_uncommitted_heading`), used by both `session-guard.sh`'s frozen-artifact rule (pattern `— decision:`) and `session-commit-guard.sh`'s Stop check (pattern `— (decision|milestone):`). `session-guard.sh` was refactored to source and call it in the same commit; its existing 16 tests were re-run and stayed green with no changes needed to the test file itself.
