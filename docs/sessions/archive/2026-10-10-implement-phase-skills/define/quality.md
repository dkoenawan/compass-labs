## Assumptions and dependencies

**Assumptions:**
- A backend that serves an HTTP API can produce or hold an OpenAPI 3.x document in the established stack's own way (generated by the framework, or written beside the code).
- The Design phase's API contract (`design/solution.md`'s frontend ↔ backend contracts) names method, path, request, response and error cases precisely enough to compare against an OpenAPI document.
- Consuming repos have a way to run unit and component tests, through a test command the Implement phase can detect, as `task-executor` does today.
- A user deciding on variations at the Implement gate is acceptable within one gate, without a separate review step.

**Dependencies:**
- The design's API contract from the Design standard (`skills/design/kinds/three-tier.md`; field-level detail from #47 once it ships): relied on by REQ-012.
- Scalar, to render the OpenAPI document: relied on by REQ-011.
- ADR-004 D7 (per-layer home) and D8 (construct owner): relied on by REQ-014 and REQ-018.
- The Close fold-back procedure (`skills/session/reference/close-foldback.md`) and `doc-maintainer`: relied on by REQ-006.
- The `verification` standard and `agents/test.md`: relied on by REQ-009 and REQ-010.
