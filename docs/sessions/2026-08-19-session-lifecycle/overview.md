# Feature Spec: Session Lifecycle

> Generated by /compass:plan | Date: 2026-08-19 | Status: Draft
> Relates to: Issue #22 — Design and implement full session lifecycle (GitHub-tracked, Diataxis-linked)

## Summary

A 10-node session lifecycle that drives every feature/update/bugfix through GitHub tracking end-to-end. `plan` stays the sole driver from Intake through Spec, sub-invoking `explore` (Research) and `adr` (ADR decision) for big sessions only, then returning control to itself. GitHub `stage:*`/`type:*`/`size:*` labels are the single source of truth for where a session sits. Execute/Validate/Close are true handoffs to domain-fanned skills. Long-running research runs as a resumable, cron-backed background agent — reusing and generalizing the checkpoint/cron pattern `task-executor` already proved.

## Layer 1 — State Model (replaces DB Layer)

### Stages

All tracked via `stage:*` label on the GitHub Issue/Project:

```
stage:intake → stage:classify → stage:discover
  → [big only] stage:research → stage:adr
  → stage:github-create → stage:spec
  → stage:execute → stage:validate → stage:close
```

### Label Taxonomy

| Label group | Values |
|---|---|
| `stage:*` | `intake`, `classify`, `discover`, `research`, `adr`, `github-create`, `spec`, `execute`, `validate`, `close` |
| `type:*` | `feature`, `update`, `bugfix` |
| `size:*` | `small`, `big` |

Labels are the single source of truth. The session's `overview.md` frontmatter mirrors the current label as cache, not authority.

### Entity Mapping

| Size | GitHub entity | Notes |
|---|---|---|
| `small` | Single Issue | Carries all labels; state transitions relabel the same issue |
| `big` | Project + linked Issues | Project carries session-level `stage:*`; each linked Issue is a construct task inheriting `type`/`size` from the parent |

### Session Artifact

`docs/sessions/{date}-{slug}/overview.md` is created at **Intake**, not at Spec approval — reversing today's `plan` behavior where the file only appears after the Phase 4 approval gate.

- On Q1 (feature description), `plan` immediately creates `docs/sessions/{date}-{slug}/overview.md` with frontmatter and a `## Summary` populated from the raw answer, `status: draft`.
- Every subsequent phase (Classify, Discover, Research, ADR, GitHub Create, Spec) appends to or edits this same file in place — it is the running record of the session, not a final-only artifact.
- This makes the session reviewable at any point, including mid-discovery — the file exists whether or not the session reaches Close. A session that gets abandoned or rethought leaves a partial, honestly-`status: draft` file rather than nothing.
- The Phase 4 approval gate no longer *creates* the file — it flips `status: draft → status: approved` on the file that's already there.

Frontmatter gains:

```yaml
issue: <N>
stage: <current stage:* value>
status: draft   # draft | approved | in-progress | complete | abandoned
```

### Bugfix Path

No separate skill. `plan` Q1/Q2 detects a bugfix from the feature description + "extends existing" answer, and short-circuits Discover straight to `stage:github-create` — Research and ADR are skipped entirely regardless of size, since bugfixes don't warrant an ADR.

## Layer 2 — Skill Wiring (replaces Backend Layer)

### Driver Span (`plan` owns, never releases control)

```
plan: Intake (Q1) → creates docs/sessions/{date}-{slug}/overview.md immediately, status: draft
  → Classify (Q2: type + size) → appends to overview.md
  → Discover (Q3 + explore-as-subagent if extending) → appends to overview.md
  → [big] Research call-out: plan invokes explore in "research mode" (Layer 3), findings appended
  → [big] ADR call-out: plan invokes adr, receives decision doc path back, linked in overview.md
  → GitHub Create: plan shells `gh issue create` / `gh project create` inline,
    applies stage:github-create → stage:spec labels, writes issue: <N> into overview.md frontmatter
  → Spec: plan finalizes overview.md, commits, flips status: draft → approved, relabels → stage:spec
```

`stage:execute` is not set by `plan` — Execute is a separate, later invocation.

The file is never absent mid-session — Discover, Research, and ADR all edit the same file that Intake created, rather than producing throwaway conversational output that only lands on disk at the end. This is what makes a session reviewable at any stage and lets an abandoned session leave an honest partial record instead of nothing.

### Handoff Span (plan exits; each invoked separately by user or cron)

```
Execute:  fans out by construct `layer` (Backend | Frontend | Database | Infra | AI-Agent)
          → calls skills/{backend,frontend,database,infrastructure}/ (currently .gitkeep stubs — need SKILL.md)
          → new: skills/ai-agent/ (net new per issue's gap audit)
          → each writes an Execution Log entry to overview.md + checks off its task-list
            item on the Issue, relabels stage:execute → stage:validate when its slice is done

Validate: fans out by test domain (Playwright-Storybook | API-contract-tests | eval-tests)
          → net-new skills, same write-back pattern, relabels → stage:close

Close:    doc-maintainer pass across all 4 Diataxis quadrants + registry construct
          status planned → built
          → relabels stage:close → closes Issue/Project
```

### GitHub Create (inline in `plan`)

```bash
# small
gh issue create --title "..." --body "..." --label "type:$TYPE,size:small,stage:github-create"

# big
gh project create --title "..." --owner dkoenawan
gh issue create --title "..." --label "type:$TYPE,size:big,stage:github-create"   # per construct task
gh project item-add <project> --url <issue-url>
```

### Frontend/Backend Boundary

Not applicable in the traditional sense — this is a skill-wiring boundary. `plan` owns Intake–Spec synchronously (blocking, conversational). Execute/Validate/Close are asynchronous handoffs, invoked independently, each self-contained and label-driven rather than plan-driven.

## Layer 3 — Research Agent Pattern (replaces Frontend Layer)

Background, resumable — reuses and generalizes `task-executor`'s cron/checkpoint pattern.

### Shared Scripts

New location: `skills/_shared/scripts/` — lifted from `skills/task-executor/scripts/`:

| Script | Reusable as-is? |
|---|---|
| `find-active-plan.sh` | Yes — generalizes cleanly |
| `install-schedule.sh` / `uninstall-schedule.sh` | Yes |
| `check-idempotency.sh` | Yes |
| `comment-on-issue.sh` | Yes |
| `select-next-task.sh`, `mark-task.sh`, `prepare-branch.sh` | No — task-list/commit specific, stay in `task-executor` |

Both `skills/task-executor/scripts/` and the new `skills/explore/scripts/` source the shared scripts rather than duplicating logic.

### Research Checkpoint File

`$SESSION_DIR/research.md`:

```yaml
---
issue: <N>
status: in-progress   # in-progress | complete | paused
schedule: "0 */6 * * *"
findings_so_far: <path to accumulated notes, or inline below>
---
```

### `explore` Research Mode (new — called only by `plan` during Research call-out, big sessions only)

1. `plan` writes `$SESSION_DIR/research.md`, commits, installs cron via shared `install-schedule.sh`, relabels `stage:research`.
2. `plan` tells the user research is running in the background; the conversation can end here — unlike today's synchronous `explore` call.
3. Cron fires `explore --research-execute`: reads `research.md`, does one research increment, appends findings, commits + pushes.
4. On completion: `explore` sets `status: complete`, uninstalls its own cron, comments a findings summary on the Issue, relabels `stage:research → stage:adr`.
5. User (or a scheduled `plan` re-invocation) resumes `plan` in `stage:adr`, which reads `research.md` findings before invoking `adr`.

Error handling reuses `task-executor`'s E3 (no active plan), E13 (lockfile/concurrent cron fire) directly rather than reinventing them for research.

## Implementation Order

### 1. State Model

1. Add `stage:*` / `type:*` / `size:*` labels to the repo (`gh label create` × N).
2. Add `issue:` / `stage:` / `status:` fields to `skills/plan/template.md` frontmatter.

### 2. Skill Wiring

1. **Move file creation to Intake**: change `plan`'s Phase 1 (Q1) to write `docs/sessions/{date}-{slug}/overview.md` immediately with `status: draft`, instead of only creating it in the current Phase 5 (post-approval). This is the reversal requested this session — every subsequent phase edits the same file in place.
2. Change the Phase 4 approval gate from "create the file" to "flip `status: draft → approved`" on the existing file.
3. Extract shared scripts to `skills/_shared/scripts/`.
4. Update `task-executor` to source the shared scripts — regression-check existing behavior is unchanged.
5. Add a GitHub Create phase to `plan` (inline `gh issue create` / `gh project create` block), inserted before the Spec-finalization phase.

### 3. Research Agent

1. Add `research.md` format + `--research-execute` mode to `skills/explore/SKILL.md`.
2. Wire cron install into `plan`'s Research call-out.

### 4. Execute / Validate Skills

1. Flesh out `SKILL.md` for `backend/`, `frontend/`, `database/`, `infrastructure/` (currently `.gitkeep` stubs).
2. Create net-new `skills/ai-agent/`.
3. Create net-new Validate skills: Playwright-Storybook, API-contract-tests, eval-tests.

### 5. Close

1. Wire `doc-maintainer` + registry status flip as a chained final phase, callable standalone or from Validate's completion.
